Подготовлено по фактически приложенному пакету 23 сентября 2026 года. Это проект решения для дальнейшей разработки, а не уже реализованный и проверенный агент. Числа ниже получены при проверке CSV; ожидаемый результат предлагаемого алгоритма ещё не измерен.

## 2 Что именно оптимизировать

Бизнес-цель кейса — максимизировать net_arpu_gain, то есть моделируемый прирост выручки за вычетом стоимости коммуникаций. Это не полноценная прибыль оператора: себестоимость услуг, удержание и долгосрочный LTV в формуле отсутствуют.

Обозначения:

- b_i — predicted_arpu клиента i;
- d_g,t — относительное изменение выручки после перехода из группы g на тариф t;
- p_g,t — вероятность перехода;
- m_c — множитель канала;
- k_c — стоимость контакта;
- r_g,t,c = d_g,t × min(p_g,t × m_c, 1);
- S_j — фактически обработанные клиенты кампании j после всех ограничений.

Для всех пилотов и финальных кампаний вместе:

    gross = sum по контактированным i [max по j, где i входит в S_j (b_i × r_i,j)]
    cost  = sum по всем j [|S_j| × k_channel(j)]
    net   = gross − cost

Для неконтактированных клиентов дополнительный эффект равен нулю. Для контактированного клиента нельзя автоматически заменить отрицательный лучший эффект нулём: скоринг берёт максимум среди проведённых кампаний, а не максимум с вариантом «ничего не делать». Это важный тест правильности оптимизатора.

Пилоты имеют две роли: дают информацию и сами влияют на итог. Шум observed_lift_ratio влияет на решения агента, но итоговый скоринг использует истинные эффекты модели, а не сумму шумных наблюдений.

## 3 Контракт и ограничения

| Ограничение | Значение и следствие |
|---|---|
| Финальный результат act | список из 1–10 словарей кампаний |
| Клиенты на кампанию | не более 5 000 фактически обработанных |
| Общие контакты | 15 000, включая пилоты и повторные контакты |
| Общий бюджет | 100 000 у.е., включая пилоты |
| Пилоты | максимум 20; запрашиваемый размер 10–200 |
| Каналы | push, sms, digital_ads, call |
| Разрешённые фильтры | ARPU-, data-, call-сегменты и текущий тариф |
| Текущие тарифы в одном фильтре | список через точку с запятой |
| Результат пилота | ratio, total, фактический размер, cost, остатки лимитов |
| Время | в основном условии 10 минут; в шаблоне 5 минут |

Проектный ориентир — укладываться в 5 минут на доступной машине, абсолютный предел по основному условию — 10 минут. Измерять фактическое время и оставлять резерв на финальную оптимизацию.

Фактический размер пилота может быть меньше 10, если сегмент или остатки ресурсов меньше запрошенного числа. Для дисперсии и учёта затрат использовать возвращённый n_customers, а не запрошенный.

Стоимость и множители каналов:

| Канал | Стоимость контакта | Множитель |
|---|---:|---:|
| push | 0 | 0,50 |
| sms | 4 | 0,65 |
| digital_ads | 22 | 0,85 |
| call | 160 | 1,20 |

Читать значения из env.channels. Бесплатный push всё равно расходует контакты и может снижать выручку.

Формат финальной кампании:

```json
{
  "campaign_name": "chosen_campaign_01",
  "filter_arpu_segment": "HIGH",
  "filter_data_segment": "HEAVY",
  "filter_current_tariff": "tariff_4;tariff_8",
  "target_tariff": "tariff_10",
  "channel": "sms"

```

Это только пример структуры, не рекомендация именно такой кампании. Не добавлять произвольные списки ID, численный лимит аудитории, top_k или фильтр predicted_arpu: они не входят в контракт финальной сдачи. explicit_ids используется внутренне для пилотов, а make_submission.py его не экспортирует.

## 4 Особенности скоринга которые определяют архитектуру

1. Кампании исполняются по порядку. Сначала учитываются пилоты, затем финальный список.
2. Внутри фильтра клиенты сортируются по ID_NUMBER по возрастанию. Сначала берутся первые 5 000, затем применяются остаток контактов и денежный лимит.
3. Сортировка по predicted_arpu внутри собственного кода не меняет фактическую аудиторию скоринга. Чтобы выделить более ценную группу, нужен разрешённый фильтр.
4. Повторная одинаковая кампания выберет тех же первых клиентов, а не следующую порцию.
5. Эффект клиента учитывается один раз по лучшей кампании, но все контакты оплачиваются.
6. Истинный эффект в выданной механике зависит от current_tariff, arpu_segment, target_tariff и канала. Data- и call-сегменты полезны для управляемого размера и состава аудитории; отдельная истинная зависимость эффекта от них в scoring_core.py не задана.
7. env.pilot_history не содержит выбранных ID и полного набора фильтров. Агент должен сам хранить параметры каждого своего запроса и связанный ответ. ID пилотов остаются неизвестны.
8. Из-за пункта 7 нельзя обещать точную дедупликацию пилотной и финальной аудитории внутри агента. Точная дедупликация доступна оценщику. Агент учитывает ожидаемое пересечение либо моделирует случайные выборки по известным фильтрам.
9. env.remaining_budget и env.remaining_contacts после act отражают затраты пилотов, но не ещё не исполненных финальных кампаний. Итоговые расходы проверять по результатам score_campaigns.
10. В local_eval поле n_campaigns включает пилоты вместе с финальными кампаниями. Ограничение 10 относится к списку, возвращаемому act.

## 5 Архитектура предлагаемого решения

Рекомендуемый минимальный стек — Python, pandas, numpy и pytest для проверок. Достаточно библиотек, уже используемых пакетом, и небольшого собственного оптимизатора. Дополнительные зависимости вводить только после измеримого выигрыша. Версии фиксировать по действительно проверенной среде.

| Компонент | Ответственность |
|---|---|
| Agent | управляет циклом, временем, исключениями и состоянием одного запуска |
| DataAudit | проверяет схему, типы, пропуски, тарифы и исторические данные |
| CandidateBuilder | формирует разрешённые комбинации сегмент — тариф — канал |
| PriorEstimator | строит слабые исторические оценки и широкую неопределённость |
| PosteriorState | обновляет оценки после пилотов |
| PilotPolicy | выбирает следующую гипотезу, канал и размер пилота |
| PortfolioPlanner | подбирает кампании с учётом порядка, пересечений и ресурсов |
| CampaignValidator | проверяет формат и фактическую исполнимость |
| DecisionLog | сохраняет объяснения, оценки, расходы и причины остановки |

Для безопасной сдачи обязательная логика может находиться в agent.py с небольшими внутренними классами. Если есть собственные модули, приложить их все и проверить импорт в чистой копии. Не рассчитывать на ноутбук, абсолютный путь разработчика или заранее обученный необъявленный файл.

LLM необязательна. Её полезные роли — структурированное предложение разнообразных гипотез и объяснение готового решения. Арифметику, ограничения и выбор кампаний контролирует код. Базовый агент должен работать без сети и ключа. Для необязательного режима: OPENAI_API_KEY из окружения, timeout, ограниченное число запросов, валидация схемы, fallback. Перед добавлением LLM проверить актуальный SDK и документацию; не привязывать решение к непроверенной версии или названию модели.

## 6 Построение кандидатов

Основная единица обучения — current_tariff × arpu_segment × target_tariff. У текущего набора 63 непустые исходные группы; при исключении перехода на тот же тариф получается до 1 260 вариантов до каналов. За 20 пилотов все проверить невозможно.

Последовательность:

1. Для каждой исходной группы посчитать число клиентов, сумму baseline, распределение baseline и качество данных.
2. Рассмотреть все допустимые целевые тарифы, исключая совпадение с текущим в обычных кандидатах. Не зашивать tariff_8 и tariff_9 как лучшие варианты.
3. Историей и характеристиками тарифов сформировать короткий список: перспективные варианты, варианты с высоким неопределённым потенциалом, несколько вариантов для разнообразия. Начальная настройка — 2–4 цели на крупную группу; это гиперпараметр, а не правило кейса.
4. Не выбирать все пилоты для одной крупнейшей группы. Например, tariff_8/HIGH содержит 4 726 клиентов, tariff_10/HIGH — 2 950, tariff_4/HIGH — 2 108; объём ещё не означает положительный эффект.
5. Для финального управления ресурсами добавить допустимые дочерние фильтры по data_segment и call_segment. Их принадлежность и ценность пересчитать по реальному профилю.
6. Объединять текущие тарифы через «;» только при совместимом действии и после проверки реального покрытия. Объединение может экономить слот кампании, но ухудшать эффект и приводить к обрезанию.

Маски аудиторий кэшировать. Для финальных кандидатов хранить фактические ID после сортировки и лимита 5 000; это локальное представление для расчётов, не поле сдаваемой кампании.

## 7 Исторические оценки без ложной уверенности

Для перехода можно вычислить относительное изменение:

    delta = (AVG_ARPU_NEXT_3M − AVG_ARPU_PREV_3M) / AVG_ARPU_PREV_3M

Околонулевой знаменатель создаёт выбросы. Фильтрацию/ограничение выбросов выбирать явно и проверять чувствительность. В mock используется порог 100 и clip[-1,3]; не переносить эти числа как доказанный закон поведения судейской аудитории.

История состоит из состоявшихся переходов. Доля переходов на тариф среди других переходов не является вероятностью отклика на предложение. Её можно использовать как слабый индикатор популярности, но нельзя выдавать за откалиброванную конверсию или causal uplift.

Практический prior:

- сглаженное среднее delta для from/to/ARPU;
- при малом числе наблюдений — смесь с уровнем from/to и более общим уровнем;
- параметры тарифов — дополнительные признаки для ранжирования неизвестных пар;
- слабый коэффициент отклика либо широкий набор сценариев конверсии;
- variance floor из-за отличий целевой аудитории от истории;
- ограничение силы prior эквивалентом небольшого числа пилотных наблюдений.

Точное значение prior и его силы подбирать на нескольких искусственных сценариях, не только на мок-модели. Проверить вариант вообще без истории: её использование должно давать измеримую пользу, а не просто усложнять проект.

Не строить соединение истории и цели по ID: пересечения нет. Для более позднего моделирования исторических исходов соблюдать время наблюдения и не включать AVG_ARPU_NEXT_3M в признаки. В первой версии достаточно агрегированных prior и пилотов.

## 8 Обновление оценок после пилотов

Для однородной группы и фиксированного канала:

    y = observed_lift_ratio
    y | theta ~ Normal(theta, 0.804² / n_actual)
    theta ~ Normal(mu0, tau0²)

После наблюдения:

    variance_new = 1 / (1/variance_old + n_actual/0.804²)
    mean_new = variance_new × (mean_old/variance_old + y×n_actual/0.804²)

Значение 0.804 — публичный параметр шума из environment.py, не секрет модели. Для смеси разных исходных групп нужно дополнительно учитывать вариацию состава; нельзя считать её однородным наблюдением и переносить средний эффект на все части.

Пример масштаба шума:

| Размер пилота | Стандартная ошибка ratio |
|---|---:|
| 30 | около 0,147 |
| 100 | около 0,080 |
| 200 | около 0,057 |

Поэтому небольшой отрицательный результат первого пилота не является достаточным основанием навсегда отвергнуть крупную перспективную группу.

Для сравнения каналов удобно хранить нормализованный эффект q = delta × p. У push, sms и digital_ads при корректной вероятности p∈[0,1] насыщения нет: y/m_c оценивает q, а дисперсия преобразованного наблюдения равна 0.804²/(n×m_c²). Это даёт перенос информации между этими тремя каналами.

У call есть насыщение при p>1/1.2. Одно наблюдение push не позволяет отдельно восстановить delta и p. Поэтому нельзя безусловно умножать push-эффект на 2,4. В первой версии звонки проверять собственным пилотом перед существенными расходами или оценивать консервативно. Если принимается p∈[0,1], отношение call/push для ненулевого эффекта находится между 2 и 2,4; при отрицательном эффекте порядок численных границ меняется.

Интервалы отражают выбранную модель неопределённости. После адаптивного отбора не называть их автоматически строгими частотными гарантиями. Проверять калибровку и чувствительность.

## 9 Адаптивный выбор пилотов

Предлагаемая первая версия — последовательный Bayesian bandit с резервом ресурсов на итоговый план. Thompson Sampling можно использовать для выбора исследуемого кандидата; это известный способ балансировать исследование и использование знаний. Здесь требуется адаптация к ограниченным контактам, денежному бюджету и совместному портфелю, поэтому обычная реализация bandit сама по себе задачу не решает.

Практическая политика:

1. Построить предварительный план на текущих posterior.
2. Выделить крупные группы, где дополнительная информация может изменить план.
3. Выбрать несколько разнообразных начальных пилотов, например 6–8 гипотез по 80–120 клиентов. Эти числа — начальная настройка для сравнения, не обязательный режим.
4. После каждого результата пересчитать posterior и весь план.
5. Следующие пилоты направлять на спорных претендентов около границы включения, недостаточно проверенных лидеров и перспективные неизученные группы.
6. Выбирать размер из 50, 100, 150, 200 либо другого допустимого набора с учётом фактической аудитории. Малый размер — когда достаточно грубой проверки, крупный — когда ошибка изменит решение для большой группы.
7. Сравнивать push и sms по стоимости получаемой информации и непосредственному риску. У push нулевая денежная цена, у sms сильнее сигнал при том же шуме. Пилот sms на 200 стоит 800 у.е.; 20 таких пилотов стоят 16 000 и занимают 4 000 контактов. Это допустимо, но не доказательство оптимальности такого расписания.
8. Останавливаться, когда полезной информации ожидается меньше, чем стоит дополнительный пилот и потерянная возможность контактировать других клиентов; либо достигнут лимит времени/ресурсов.

Для улучшенной версии использовать оценку ценности информации: смоделировать несколько возможных ответов очередного пилота, обновить posterior, заново решить портфель и сравнить ожидаемый результат с вариантом остановки. Включить стоимость, непосредственный эффект самого пилота, неизвестное пересечение и расход контактов. На практике использовать небольшое фиксированное число симуляций и shortlist, чтобы уложиться во время.

Упрощённая эвристика вместо дорогой симуляции — ранжирование по объёму baseline группы, posterior uncertainty и вероятности изменить выбранное действие. Обязательно обозначать её как эвристику, а не точный value of information.

Не расходовать все 20 пилотов только потому, что это разрешено. При этом минимум один успешный вызов пилота обязателен для условий кейса.

## 10 Выбор канала и оптимизация портфеля

Для однородной, непересекающейся кампании с N клиентами и суммарным baseline B:

    expected_net = B × E[r] − N × cost_per_contact
    conservative_net = B × (E[r] − lambda × SD[r]) − N × cost_per_contact

lambda — настраиваемое отношение к риску. Если uncertainty относится к общему эффекту группы, нельзя уменьшать её как 1/sqrt(N) только потому, что клиентов в финальной кампании много: параметр остаётся общим.

Выбор более дорогого канала оправдан, если дополнительный эффект больше дополнительной стоимости и он выгоднее альтернативного использования бюджета:

    B × (r_expensive − r_cheap) > N × (cost_expensive − cost_cheap)

Учебный пример, не результат по данным: 1 000 клиентов со средним baseline 5 000, q=0,10, без насыщения. Push даёт net 250 000; SMS — 321 000; digital_ads — 403 000; call без насыщения дал бы 440 000, но потребовал бы 160 000 бюджета, то есть полный вариант недопустим. Это показывает, почему сравнения ROI или одной конверсии недостаточно.

Первая рабочая версия оптимизатора:

- кэшировать фактические маски кандидатов;
- выбирать кампании по положительному добавочному эффекту для всего текущего плана;
- учитывать уже покрытых клиентов через лучший эффект, а расходы — по каждому контакту;
- учитывать деньги, контакты и максимум 10 финальных кампаний;
- сравнивать несколько способов построения плана: абсолютный marginal gain и варианты со штрафами за ресурсы;
- сделать ограниченный beam search или локальные замены: удалить/добавить/заменить кампанию, поменять канал и порядок;
- после каждого изменения пересчитывать обрезание в точном порядке исполнения;
- остановиться по фиксированному числу итераций и резервному временному пределу.

Простой greedy по gain/cost некорректен для бесплатного push и не гарантирует лучший портфель. Использовать его только как один из baseline.

Более сложный MILP возможен после MVP, но порядок кампаний и зависимое обрезание усложняют модель. Безопаснее сначала генерировать исполнимые варианты покрытия, решать приближение, затем точно проигрывать финальный список. Не объявлять решение глобально оптимальным без соответствующего доказательства/solver gap.

Неизвестные пилотные ID: сохранять фильтры и n_actual каждого пилота. Для одного пилота в сегменте размера M вероятность попадания клиента — n/M. Для нескольких пересекающихся пилотов можно генерировать случайные подвыборки с фиксированным RNG и оценивать expected deduplicated net портфеля. Это приближение; агент не должен получать реальные ID из internals.

Для MVP можно предпочесть непересекающиеся финальные группы и консервативную поправку за пилотное пересечение. Отдельно измерить, меняет ли более точное моделирование выбор плана.

## 11 Поведение при неудачах и отрицательных результатах

Не использовать broad except с молчаливым продолжением. Каждую ошибку записывать с контекстом. Перед пилотом проверять сегмент и остатки. После ошибки перечитывать публичное состояние env, поскольку нельзя считать, что операция точно ничего не потратила.

После каждого успешного обновления хранить лучший корректный финальный план в памяти. При ошибке необязательного компонента вернуть этот план. Не сохранять знания о скрытой среде между независимыми запусками.

Есть конфликт: условие требует 1–10 финальных кампаний, но все проверенные действия могут оказаться невыгодными. Для сдачи резервировать малый непустой допустимый вариант и выбирать минимальный ожидаемый ущерб, явно фиксируя отсутствие уверенно положительного варианта. Не подставлять фиктивный пустой фильтр и не считать переход на тот же тариф гарантированным нулём: это не обещано контрактом. Не гарантировать прибыль на любом скрытом сценарии.

В промышленном продукте корректнее разрешить abstain — отказ от запуска при отрицательной ожидаемой ценности. Это развитие продукта, а не самовольное изменение конкурсного контракта.

Смысловые тесты:

1. Разрешённые фильтры, NaN, неизвестные категории и пустые сегменты.
2. Обрезание по ID при 5 001 клиентах, остаток бюджета меньше стоимости одного платного контакта.
3. Повторные контакты увеличивают затраты, но не удваивают эффект.

5. При пересечении клиент получает лучший эффект, даже если он не от последней кампании.
6. Пилот с фактическим n меньше запрошенного корректно меняет дисперсию и ресурсы.
7. Слабый отрицательный пилот не равен доказательству отрицательного эффекта.
8. Разные ответы заглушки run_pilot приводят к разным решениям.
9. Смена порядка кампаний может менять фактическое покрытие и результат.
10. Масштабирование push/sms/ads корректно; насыщенный call не экстраполируется линейно.
11. Все отрицательные эффекты, нулевой бюджет, малый остаток контактов, отказ необязательной LLM.
12. Новый Agent не наследует posterior предыдущего запуска; фиксированный RNG обеспечивает воспроизводимость.
13. Нельзя импортировать mock_model/организаторские internals в агент или извлекать closure.
14. Повторный make_submission создаёт те же кампании; финальный формат не содержит explicit_ids.

Сравнения на одинаковых seed: исходный agent_template, история без адаптации (только исследовательский baseline, не финальная сдача), фиксированный набор пилотов, предложенный adaptive агент.

Метрики: net_arpu_gain, gross, стоимость, контакты, уникальный охват, число пилотов, число финальных кампаний, runtime, среднее/медиана/минимум и p10 результата, доля отрицательных прогонов. При 10 прогонах p10 — грубая оценка хвоста, не статистическая гарантия.

Изменение seed в local_eval меняет шум и случайную пилотную выборку, но не семейство истинных мок-эффектов. Поэтому нужны собственные тестовые среды с разными таблицами эффектов: перестановка лидеров, изменение знаков, слабая связь с историей, низкая конверсия, насыщение звонков, почти нулевые эффекты. Создавать их в тестовом harness через публичную фабрику; агенту передавать только env. Не заявлять, что эти среды воспроизводят секретную модель.

Ablation: без prior; без адаптации; без поправки на uncertainty; один канал; без учёта пересечений. Проверить, какие компоненты реально полезны.

Цель — улучшить baseline на разных сценариях при соблюдении лимитов. Не подгонять критерий приёмки под придуманную сумму прибыли. Если превосходство не подтверждено, показать фактический результат и ограничение.

## 15 Развитие после хакатона

Промышленная версия потребует самостоятельной постановки: реальная контрольная группа, измерение инкрементального эффекта, история предложений и отказов, возможность не запускать кампанию, ограничения частоты контактов, наблюдение за оттоком и долгосрочной выручкой. Обучение causal uplift возможно после появления подходящих данных о воздействии и контроле; текущая история переходов сама по себе этого не обеспечивает.

В интерфейсе аналитика полезны бюджет, ожидаемый эффект и диапазон неопределённости, причины выбора, расход на исследование, сравнение сценариев и экспорт плана. Не выдавать симуляторный expected net за обещанный реальный доход. Реальные коммуникации и подключения к операторским системам в конкурсную реализацию не входят.

I. Pilot overlap: реальные пилотные ID агенту не известны. Не получай их через обход интерфейса. Оцени пересечения по фильтрам и n или Monte Carlo с фиксированным RNG; обозначь приближение. Финальное покрытие между финальными кампаниями рассчитывай точно.
J. Fallback: сохраняй текущий корректный план после обновлений. При отказе необязательного компонента верни его. При всех отрицательных оценках соблюди требование непустого финального плана минимальным ожидаемым ущербом и явно запиши риск; не выдумывай гарантированно безопасное действие. Не создавай фиктивные пустые кампании.

РЕАЛИЗАЦИЯ
Python + pandas + numpy; добавляй зависимости только по необходимости. Ядро работает без сети и LLM. Желательно держать обязательную логику самодостаточной в agent.py; если есть модули, включи все в сдачу. Не создавай зависимость от рабочего каталога разработчика или notebook state. Историю читай относительно поставляемых файлов и документируй fallback, если она недоступна.

Все собственные случайные решения используют локальный RNG с фиксированным seed, совместимым с SUBMISSION_SEED=42. Не считывай скрытый seed среды. Не используй системное время для выбора кампаний; таймер нужен только для аварийного предела. Основную сложность ограничь фиксированным числом итераций, чтобы обычные запуски были воспроизводимыми.

LLM необязательна: добавляй только после готового ядра, с OPENAI_API_KEY из окружения, timeout, валидацией и fallback. По умолчанию не должна влиять на воспроизводимый submission. Не публикуй и не отправляй реальные кампании.
