## 1. Разобраться с исходным состоянием

Прочитай применимые `AGENTS.md`, `skill.md`, корневой README, README backend/frontend, `docs/team/API_CONTRACT.md`, `docs/ARCHITECTURE.md`, `docs/ACCEPTANCE.md` и существующие командные промпты. Старые промпты объясняют замысел; текущий код определяет, что уже реализовано.

Проверь `git status --short`, ветку, remote, историю, staged/unstaged diff и untracked-файлы. Перед объединением с GitHub обеспечь восстановимость всей локальной работы, включая новые файлы. Затем выполни `git fetch origin`, сравни историю и содержимое обеих сторон. Не делай слепой pull поверх изменений, `reset --hard`, `clean` или force-push. Если объединение необходимо для завершения интеграции, сохрани нужные изменения обеих версий и разреши конфликты по фактическому контракту. Не считай удалённую версию автоматически более полной.

Кратко сообщи реальные проблемы и начинай исправления. Не останавливайся на аудите или плане. Ограничь изменения тем, что нужно для готовности и интеграции; не начинай новый цикл оптимизации алгоритма без выявленной причины.

## 2. Проверить и завершить сквозную работу

Проверь цепочку: интерфейс → настоящий FastAPI → worker → `Agent().act(env)` → отдельная локальная оценка → SQLite → отображение результата → экспорт.

Обязательные свойства:

- Frontend по умолчанию использует настоящий API. Демо включается явно и обозначается в UI; сетевой сбой не подменяется демонстрационными данными.
- Создание run быстро возвращает управление; вычисление выполняется одним worker, HTTP остаётся доступным. Повтор POST после потери ответа использует прежний `Idempotency-Key` и возвращает тот же run. Другая конфигурация с тем же ключом и второй активный запуск обрабатываются согласно API-контракту.
- Polling, ETag/304, переход по прямой ссылке и reload сохраняют связь с выбранным run. При обрыве соединения остаётся последний snapshot и понятная ошибка; восстановление продолжает наблюдение за тем же запуском.
- SQLite сохраняет историю, snapshots и ключи идемпотентности. Завершённые результаты неизменяемы. Аварийно прерванные задания получают предусмотренный статус; второй сервер с той же БД не повреждает живой запуск.
- CSV и JSON берутся из сохранённого завершённого run и не запускают агента повторно. Скачанное через UI содержимое совпадает с экспортом API.
- `forecast`, `pilots` и `local_evaluation` имеют разный смысл и отображаются отдельно. Нерассчитанные значения остаются `null`; отрицательные результаты видны. `net_arpu_gain` — прирост выручки минус стоимость контактов, а не полная прибыль оператора.
- Перенос `uniflow` → `orbitduo` согласован в исполняемых импортах, тестах, конфигурации и поставке. Архивные названия и имя GitHub-репозитория не требуют механического переименования.

Сохрани автономность конкурсного агента: он работает без backend, сети и API-ключей, использует публичный `env`, а оценщик не поставляет ему скрытые ответы. Организаторские evaluator, шаблон и исходные CSV не изменяй. `submission.csv` создавай штатным генератором.

Проверь минимум один успешный пилот, 1–10 допустимых непустых финальных кампаний, ограничения бюджета и контактов с учётом пилотов, аудиторию до 5 000 на кампанию и воспроизводимость при seed 42. Одного успешного exit code `local_eval.py` недостаточно: он может перехватывать ошибки агента.

## 3. Подтвердить результат проверками

Сначала проверь доступное окружение и актуальные зависимости. Не переустанавливай исправное окружение без необходимости. Ниже — существующие команды; выполняй их из указанного каталога и адаптируй к фактически найденному Python.

Из корня:

```powershell
$env:PYTHONUTF8 = '1'
.\.venv\Scripts\python.exe -m pytest participant_package/tests backend/tests -q
```

Из `participant_package/`:

```powershell
..\.venv\Scripts\python.exe local_eval.py
..\.venv\Scripts\python.exe make_submission.py
..\.venv\Scripts\python.exe -m orbitduo.evaluation
..\.venv\Scripts\python.exe -m experiments.verify_delivery
```

Дополнительно проверь повторную генерацию CSV при seed 42 и совпадение SHA-256. После актуализации submission запусти из корня:

```powershell
.\.venv\Scripts\python.exe -m backend.final_smoke
```

Из `frontend/`:

```powershell
npm run build
npm run lint
npm run test
npm run test:e2e
```

Проверь полный стек в отдельном Compose-проекте с отдельным томом и свободными портами, чтобы проверки перезапуска не затронули существующие пользовательские запуски. Базовые команды из корня:

```powershell
docker compose up -d --build --wait
.\.venv\Scripts\python.exe -m scripts.verify_stack --restart
```

Перед выполнением изучи параметры скрипта и согласуй адреса с выбранными портами. Затем из `frontend/` задай `ORBITDUO_BASE_URL` фактического приложения и выполни `npm run test:e2e:live`. Этот тест сам не запускает сервер.

Если Docker недоступен, проверь настоящий backend и Vite локально; отдельно укажи, что контейнерный запуск не подтверждён. При сравнении CSV между Windows и Linux учитывай окончания строк; побайтное совпадение проверяй внутри одной платформы.

Используй существующие тесты. Добавляй регрессионные проверки для найденных существенных ошибок. Не повторяй полный набор без новых изменений или причины и не запускай длительные исследовательские бенчмарки ради проверки интеграции.

## 4. Документация и сдача работы

Обнови инструкции запуска и приёмки по фактическому результату. Если нужен отдельный сценарий демонстрации, создай `docs/DEMO.md`: запуск приложения, создание плана, пилоты, результат, reload, история, экспорт. Укажи действующие адреса и команды без путей с чужого компьютера.
