# Промпт 1 — backend, агент и проверяемое решение кейса

Ты — первый разработчик в команде из двух человек. Полностью реализуй вычислительное ядро, конкурсного агента и backend продукта **OrbitDuo Campaign Studio** для кейса Beeline Tariff Marketing Campaigns. Второй разработчик параллельно реализует frontend. Нужны работающий код, измеренные результаты и интеграция по общему API.

Сначала прочитай `docs/team/API_CONTRACT.md`: это общий договор двух частей. Работай до готовых артефактов и проверок; обычные инженерные решения принимай самостоятельно. Не ограничивайся планом и псевдокодом. Не обещай гарантированной прибыли на неизвестных эффектах: докажи работоспособность, корректность ограничений и измеренное качество стратегии.

## 3. Обязательная конкурсная часть

Сохрани точку входа `participant_package/agent.py`, `class Agent`, `act(self, env) -> list[dict]`. `Agent()` без аргументов обязан работать в исходных скриптах. Допустимы собственные модули рядом, если они включены в сдачу и корректно импортируются из чистой копии.

Обязательные условия:

- От 1 до 10 финальных кампаний, допустимые тарифы и каналы, непустая фактическая аудитория.
- До 5 000 клиентов на кампанию, всего до 15 000 контактов и 100 000 у.е., включая пилоты и повторные контакты.
- До 20 пилотов с запрашиваемым размером 10–200. Минимум один успешный пилот, реально влияющий на решение.
- Финальная кампания содержит только `campaign_name`, `filter_arpu_segment`, `filter_data_segment`, `filter_call_segment`, `filter_current_tariff`, `target_tariff`, `channel`. Фильтры можно опускать или задавать `None`, текущие тарифы перечисляются через `;`.
- В финальном результате нет `explicit_ids`, `top_k`, численного лимита аудитории и произвольного фильтра по доходу.
- Тарифы и параметры каналов читай из публичных `env.tariffs`, `env.channels`; бюджет и контакты — из текущего публичного состояния.
- Агент использует только разрешённые поля/методы среды. Никаких `__closure__`, `gc`, introspection скрытого RNG, `internals`, импорта mock-модели или обращения к скорингу истинных эффектов в решающем контуре.
- Основной гайд даёт 10 минут, шаблон — 5. Прими более строгий внутренний предел 5 минут с резервом на финализацию; замерь фактическое время и не строй стратегию, требующую десятиминутного лимита.
- Базовая сдача работает offline, без LLM, веб-сервера, внешней БД, GPU и ключей.

## 4. Цель и точная механика

Максимизируй `net_arpu_gain = gross_gain − communication_cost`. Это дополнительная выручка за вычетом контактов, не полная прибыль оператора. `predicted_arpu` — базовая ожидаемая выручка клиента, не эффект кампании.

Для клиента эффект кампании: `baseline × delta × min(conversion × channel_multiplier, 1)`. По каждому контактированному клиенту учитывается лучший эффект среди всех его кампаний; стоимость начисляется за каждый контакт. Если все эффекты отрицательные, лучший отрицательный эффект остаётся отрицательным. Инициализация через `max(0, эффект)` для уже контактированных клиентов ошибочна.

Пилоты идут до финальных кампаний. Финальные фильтры выбирают клиентов по возрастанию `ID_NUMBER`, затем действуют предел 5 000, остатки контактов и денег. Порядок кампаний влияет на итог. Повтор одинакового фильтра снова выбирает первых клиентов, а не следующую страницу аудитории. Сортировка внутри собственного алгоритма по ARPU не меняет правила оценщика.

Публичное `env.pilot_history` не содержит ID пилотов и полного набора фильтров. Сохраняй собственные запросы, ответы и остатки. Не обещай точного пересечения с пилотами: оно неизвестно агенту. Пересечение финальных кампаний рассчитывай точно; пилотное — оценивай по известным фильтрам и размерам с явно описанным приближением.

## 5. Практичный алгоритм

Реализуй прозрачные модули: аудит → кандидаты → исторический prior → posterior пилотов → выбор следующего эксперимента → оптимизация портфеля → валидация → журнал. Избегай тяжёлой инфраструктуры, не дающей измеримого выигрыша.

### Кандидаты и предварительные оценки

Основная группа — `current_tariff × arpu_segment`. Для неё рассмотри все допустимые целевые тарифы, затем сформируй короткий разнообразный список по ожидаемому денежному потенциалу, неопределённости и объёму baseline. Не зашивай лучшие названия тарифов и не отправляй все пилоты в одну крупнейшую группу.

Для исполнения добавляй разрешённые data/call-фильтры, чтобы управлять размером аудитории, а совместимые исходные тарифы объединяй только после проверки реального покрытия. Кэшируй маски и отсортированные аудитории. Обычные кандидаты не предлагают переход на тот же тариф; не считай такой переход гарантированно безопасным fallback.

Исторический prior: сглаженная оценка относительного изменения ARPU по from/to/сегменту с fallback на более общие группы, обработкой малых знаменателей и выбросов. История содержит только состоявшиеся переходы: их частоты не являются откликом на предложения, causal uplift или точной вероятностью конверсии. Используй историю как слабое ранжирование, широкую неопределённость и ограниченную силу prior. Проверяй чувствительность к параметрам и вариант без истории.

### Обновления по пилотам

Для однородной группы в одном канале наблюдается `y = observed_lift_ratio` с дисперсией `0.804² / n_actual`, по публичной механике среды. Используй фактически возвращённый `n_customers`, а не запрошенный. Он может быть меньше десяти из-за размера сегмента или остатка ресурсов.

Для нормального prior `N(mu, v)` и дисперсии наблюдения `s²`:

```text
v_new = 1 / (1/v + 1/s²)
mu_new = v_new * (mu/v + y/s²)
```

Учти численную устойчивость и ненулевой variance floor. Смешанный пилот нельзя трактовать как независимое однородное наблюдение всех его подгрупп; в MVP исследуй однородные группы.

Для push/sms/digital_ads в текущих множителях допустима нормализация `q = y / multiplier`, с дисперсией `0.804² / (n_actual × multiplier²)`. Перенос валиден при вероятности в [0,1] и отсутствии насыщения. Проверь это условие по фактическим параметрам каналов.

Для звонков есть насыщение `min(p × 1.2, 1)`. Одно push-наблюдение не разделяет эффект перехода и конверсию. В MVP либо проверяй call собственным доступным пилотом, либо не включай его без достаточных данных. Не экстраполируй call всегда как push × 2.4. Полностью бесплатный push всё равно расходует контакты и может иметь отрицательный эффект.

### Адаптивные эксперименты

Начни с разнообразных перспективных гипотез, далее направляй пилоты туда, где уточнение способно изменить итоговый портфель. Сравни несколько допустимых размеров с учётом точности, затрат и оставшихся возможностей. Слабый отрицательный пилот — повод пересчитать неопределённость, не автоматически навсегда отвергнуть группу.

Допустимы posterior sampling или ограниченная эвристика ценности информации: объём baseline × неопределённость × возможность изменить решение, с учётом расходов и возможного вреда пилота. Эвристику не называй точным оптимумом. После каждого ответа обновляй оценки и текущий план. Останавливай исследование, когда ожидаемая польза ниже затрат/риска, а не обязательно на двадцатом пилоте.

Резервируй ресурсы для финального непустого исполнимого плана. Пилоты сами входят в результат; не оптимизируй только финальную часть, игнорируя уже проведённые контакты.

### Портфель

Для простой однородной аудитории с N клиентами и суммой baseline B: `expected_net = B × E[r] − N × contact_cost`. Для реального портфеля считай предельный эффект с учётом предыдущих кампаний, пересечений, порядка и ресурсов.

Начни с корректного marginal-gain greedy и нескольких штрафов за ограниченные ресурсы. Затем добавь ограниченный по итерациям beam search либо локальные замены кампаний/каналов/порядка, только если это улучшает результаты. Не полагайся на gain/cost: у push нулевая стоимость, а контакты и десять слотов тоже ограничены.

Пересечения с пилотами оценивай аналитически либо небольшим Monte Carlo с собственным фиксированным RNG; сохраняй допущения и сравни влияние приближения на выбор. Общую неопределённость эффекта группы нельзя искусственно уменьшать в sqrt(N) раз из-за большой финальной аудитории.

Введи режимы balanced/conservative через документированный риск-штраф на неопределённость. Консервативный режим не обещает, что все исходы окажутся прибыльными. Финальный план полностью проиграй по публичным правилам и проверь все ограничения.

### Сбои и воспроизводимость

Сохраняй лучший корректный план после обновлений, логируй ошибки с контекстом, после ошибки пилота перечитывай остатки. Не скрывай исключения широким `except: pass`. При всех отрицательных оценках соблюди конкурсное требование 1–10 кампаний: выбери непустой вариант с минимальным оценённым ущербом в оставшихся ресурсах и явным предупреждением. Не подставляй пустые фиктивные фильтры.

Состояние нового `act` не наследует posterior предыдущего запуска. Локальный RNG, стабильные tie-breakers и ограничение по числу итераций делают стандартный `Agent()` воспроизводимым. Таймер — аварийная граница, не основной источник выбора действий. В UI seed задаёт конфигурацию нового локального эксперимента; стандартная конкурсная генерация использует предусмотренный make_submission seed 42.

## 6. API и наблюдаемость для frontend

Реализуй **все** маршруты и DTO из `docs/team/API_CONTRACT.md`. Pydantic и OpenAPI служат машинно проверяемой реализацией схем. Единый формат ошибок, корректные HTTP-статусы, `null` вместо NaN, UTC-время. Не выдавай пустые заглушки за готовый расчёт.

Долгий запуск не блокирует HTTP event loop: один выделенный worker, атомарная регистрация активного задания и SQLite/локальные артефакты для сохранения. POST быстро возвращает run_id; frontend читает snapshots polling-запросами. Идемпотентность и восстановление после перезапуска обязательны. Один локальный процесс сервера достаточно; не добавляй распределённую очередь.

Для прогресса добавь необязательный observer/callback агента, безопасный для конкурсного `Agent()` без аргументов. Callback публикует факты: построены кандидаты, выбран пилот, получен ответ, пересчитан план. Ошибка наблюдаемости не меняет решения и не обрушает вычисление. Не раскрывай скрытые рассуждения; объяснения — конкретные причины выбора, данные и допущения.

Код сервиса создаёт независимую среду на каждый запуск. Agent получает только публичный env. Только отдельный evaluation adapter после завершения стратегии может использовать организаторскую часть локального harness для официальной оценки; результат не подаётся обратно в стратегию. Импорты mock/оценщика не должны проникать в agent/decision-модули.

В DTO строго раздели posterior-прогноз, наблюдения пилотов и итог локального оценщика. Интервал показывай только при реальном расчёте с указанным методом; иначе `null`. Причины кампаний формируй из фактических оценок и pilot ids, а не шаблонными обещаниями успеха.

Экспорт `/campaigns.csv` строится из сохранённого плана конкретного run. Не вызывай `make_submission.py` для этого экспорта: он создаст другой эксперимент. Официальный submission генерируется отдельно штатной командой и проверяется на воспроизводимость.

Не добавляй LLM в обязательный путь. Сначала полностью заверши офлайн-решение и интеграцию. Реальные коммуникации и внешние рекламные API не входят в проект.

## 7. Проверки, которым можно доверять

Сначала замерь исходный `agent_template` в отдельном harness на одинаковых seed, сохрани baseline без изменения организаторских файлов. Проверь реальные зависимости: существующие pins в requirements не считать автоматически установленными/совместимыми; зафиксируй только действительно проверенную среду.

Смысловые тесты:

- фильтры, пропуски и пустые аудитории; случай 5 001 клиента и сортировка ID;
- исчерпание бюджета/контактов, бесплатный push, дорогой call, повторные контакты;
- отрицательный максимум эффекта и пересечение с лучшей не последней кампанией;
- размер пилота меньше запроса, posterior на ручном примере, перенос между каналами;
- насыщение call; разные ответы пилота меняют дальнейшее решение;
- все отрицательные варианты, корректный fallback и отсутствие утечки состояния;
- API: идемпотентность, запрет двух активных расчётов, сериализация, failed status, рестарт;
- CSV совпадает с сохранённым run и не содержит дополнительных полей.

Из `participant_package/` выполни:

```powershell
python local_eval.py
python local_eval.py --runs 10
python make_submission.py
python -m pytest -q
```

Запусти генерацию submission ещё раз и сравни байты/хэш. Проверяй не только exit code: local_eval перехватывает ошибки агента, поэтому явно проверь наличие 1–10 финальных кампаний, успешных пилотов, отсутствие отброшенных кампаний и фактическое соблюдение лимитов.

Сравни исходный шаблон, фиксированную разведку и адаптивную стратегию на одних seed. Отчёт: mean/median/min/p10 net, доля отрицательных запусков, стоимость, контакты, уникальный охват, пилоты, финальные кампании, runtime. p10 по десяти запускам — грубая оценка, не гарантия.

Смена seed в local_eval меняет шум и выборки, но не семейство истинных эффектов. Добавь отдельные тестовые сценарии через публичную фабрику: перестановка лидеров, смена знаков, слабая связь с историей, низкая конверсия, насыщенные звонки, почти нулевые эффекты. Agent не получает таблицы этих моделей. Сделай ограниченный ablation без prior, без адаптации, без риск-штрафа и с одним каналом. Если усложнение не помогает, оставь более простой вариант и покажи данные сравнения.
