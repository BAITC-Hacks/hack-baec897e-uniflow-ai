# Промпт 2 — премиальный frontend и понятный UX

Ты — второй разработчик в команде из двух человек: senior frontend engineer и product designer. Полностью реализуй frontend **OrbitDuo Campaign Studio**, рабочего инструмента для маркетингового аналитика в кейсе Beeline. Первый разработчик параллельно делает Python-агента и FastAPI по `docs/team/BACKEND_PROMPT.md`.

Сначала прочитай `docs/team/API_CONTRACT.md`, затем `participant_package/PARTICIPANT_GUIDE.md` и продуктовую часть `beeline_solution_and_codex_prompt.md`. Общий API уже согласован в файле контракта. Работай в `frontend/`; backend, агент, данные и общий контракт принадлежат другой части команды.

Нужен презентабельный, премиальный и полностью работающий интерфейс. Он должен за минуту объяснить человеку без ML-подготовки: какую задачу решаем, что агент проверил, какой план предлагает, сколько это стоит и насколько уверенно можно оценить эффект. Сделай готовое приложение с реальными состояниями и интеграцией, не только красивый экран.

## 1. Продуктовая история

Пользователь — маркетинговый аналитик, которому нужно распределить ограниченные контакты и бюджет между тарифными предложениями. Основной сценарий:

**Оценить аудиторию → начать подбор → увидеть проверку гипотез → понять предложенный план → скачать результат.**

Основная кнопка — «Подобрать кампании». Во время работы — «Агент проверяет гипотезы». На результате — «План готов» и «Скачать план CSV». Не используй «Запустить рассылку»: приложение ничего не отправляет настоящим клиентам.

В интерфейсе постоянно, но ненавязчиво виден режим «Локальная симуляция · синтетические данные» либо «Демо». Нет заявлений о реальной прибыли Beeline, выдуманных клиентов, доходности и live-интеграций.

## 2. Визуальное направление

Ощущение — дорогой, спокойный B2B-инструмент с отличной типографикой, плотностью данных и вниманием к деталям. Бренд: **OrbitDuo**, подпись **Campaign Studio**, небольшая отметка **Beeline case**. Не выдавай проект за официальный промышленный продукт оператора.

Предпочтительное направление:

- Светлый тёплый фон `#F7F7F2`, белые рабочие поверхности, почти чёрный текст `#171917`, приглушённый вторичный текст; тонкие границы и редкие мягкие тени.
- Фирменный жёлтый `#FFD600` для основного действия и небольших акцентов. На жёлтых кнопках — тёмный текст. Зелёный — только положительный результат, красный — ошибка/отрицательный эффект, янтарный — неопределённость.
- Спокойная тёмная боковая навигация допустима; не окрашивай весь интерфейс в чёрно-жёлтый. Не используй декоративные градиенты как главный дизайн-приём.
- Читаемый шрифт с кириллицей, например локально подключённый Manrope, либо качественный системный fallback. Не делай работу интерфейса зависимой от загрузки шрифта из сети.
- Сетка отступов 4/8 px, аккуратные радиусы примерно 12–16 px, согласованные кнопки/поля/таблицы, tabular-nums для метрик, ясная иерархия заголовков.
- Иконки из одного согласованного набора. Графики строятся из данных. Декоративные изображения и сгенерированные картинки для этого интерфейса не требуются.
- Ненавязчивые переходы около 150–220 ms, поддержка reduced motion. Анимация подчёркивает смену состояния, не имитирует работу алгоритма.

Создай design tokens: цвет, типографика, spacing, radius, border, shadow, focus и состояния элементов. Сначала определись с композицией главного экрана и результата, затем выдержи её во всех деталях. Избегай множества одинаковых KPI-карточек, огромных пустых hero-блоков и маленьких нечитаемых подписей.

## 3. Четыре рабочих раздела

### Обзор — `/`

Компактная боковая навигация: «Обзор», «Аудитория», «Запуски». В header — название страницы, режим данных и статус подключения. Основное пространство отвечает на вопросы «Что доступно?» и «Что сделать дальше?».

Покажи фактическую аудиторию и сумму базовой ожидаемой выручки, отдельно лимиты кампаний и исследования. Поясни baseline простыми словами: «Ожидаемая выручка без новых кампаний». Не выдавай её за заработок алгоритма.

Основной блок — «Найдём кампании с наибольшим ожидаемым эффектом» с коротким объяснением «Агент проверит предложения на небольших группах и соберёт план в заданных лимитах» и одной заметной кнопкой «Подобрать кампании».

Покажи последний запуск, если он есть, и короткий блок качества данных. Исключённые записи и причины не скрывай. При отсутствии запусков нужен уверенный empty state с полезным следующим действием, без нарисованной истории успехов.

### Аудитория — `/audience`

Сводка сегментов по текущему тарифу и уровню выручки, размеры групп, средний ожидаемый ARPU, качество данных. Понятные подписи: «Низкая / средняя / высокая выручка» с техническим кодом в деталях. Не меняй значение исходного сегмента.

Поиск по тарифам, фильтр по сегменту, сортировка таблицы и видимое число результатов. Сегменты с пропусками показаны отдельно как «Не указан» и объяснены. Не создавай персональную CRM с карточками всех клиентов: для задачи достаточно агрегатов из `/overview`.

Один полезный график состава аудитории с понятными подписями; таблица содержит те же доступные точные значения. Не добавляй временной график, если API не предоставляет временной ряд.

### Запуск и живой прогресс — `/runs/new`, `/runs/:id`

Форма запуска короткая: режим риска «Сбалансированный / Осторожный» с конкретным пояснением и фиксированные конкурсные лимиты. Seed 42 находится в раскрываемом блоке «Для воспроизводимости». Бюджет и число доступных пилотов не редактируются: публичный оценщик использует конкурсные ограничения.

После отправки сразу открывай страницу созданного run. Покажи текущий этап, фактический журнал событий и последние пилоты. Например: «Проверяем предложение для сегмента с высокой выручкой» — только если это соответствует данным backend.

Счётчики «Проверено гипотез: 6 из максимум 20», затраты пилотов и использованные контакты. Не превращай это в «30% готовности»: агент может остановиться раньше. Покажи прошедшее время, но не выдумывай точное время до завершения.

В журнале пилота: кого проверили, какой тариф/канал, фактическая выборка, наблюдаемый эффект и что изменилось в решении. Небольшая отрицательная оценка не автоматически маркируется как окончательный провал: наблюдение шумное.

Повторный клик не создаёт дубликат; сетевой повтор POST использует тот же Idempotency-Key. Если backend сообщает активный запуск, предложи открыть его. При обновлении страницы наблюдение возобновляется по run_id. Навигация по приложению не останавливает backend-расчёт.

Не добавляй кнопку остановки, если у backend нет соответствующего endpoint. Кнопка «Повторить расчёт» после ошибки создаёт новый run осознанно, а кнопка восстановления соединения лишь снова читает существующий.

### Готовый план и история — `/runs/:id`, `/runs`

После завершения оставь пользователя на том же run и покажи обзор решения. На первом плане — прогноз дополнительной выручки за вычетом коммуникаций, коммуникационные расходы, контакты и уникальный охват с ясными подписями. Включённые пилоты явно обозначены.

Два разных источника результата визуально разделены:

1. **Прогноз агента**: ожидаемый эффект и рассчитанный диапазон неопределённости. Если диапазона нет, не выдумывай его.
2. **Локальная проверка**: фактический результат оценщика на синтетической mock-модели. Подпись «Не прогноз результата скрытой проверки и не реальный доход».

Центр экрана — таблица плана, не набор декоративных графиков. Колонки: порядок, аудитория, целевой тариф, канал, контакты, стоимость, оценённый дополнительный вклад, обоснование. Сортировка таблицы меняет только представление; номер реального исполнения остаётся видимым и не меняется.

Клик открывает drawer кампании: понятное описание аудитории, точные фильтры, предложение, канал, причины выбора, использованные пилоты и неопределённость. Различай «Подтверждено пилотами», «Предварительная оценка» и «Резервный вариант». Не рисуй проценты уверенности, которых нет в API.

Распределение бюджета между пилотами, финальным планом и остатком удобно показать одной горизонтальной полосой с числами. Контакты и уникальные люди — разные значения. На выбранных диаграммах tooltip не должен быть единственным способом прочитать число.

Отрицательный прогноз или слабые данные — отдельное содержательное состояние: «Уверенно выгодные варианты не найдены» и фактическое объяснение. Не прячь минус, не рисуй зелёную галочку успеха стратегии. Техническая корректность плана и его ожидаемая выгодность — разные свойства.

Экспорт: «Скачать план CSV» и «Скачать отчёт JSON». Это файлы сохранённого текущего запуска, не повторный расчёт. Рядом коротко объясни, что конкурсный submission создаётся отдельно штатной командой. До completed экспорт отключён с причиной.

История `/runs`: дата, риск-профиль, статус, прогноз и локальный результат в разных колонках, переход к сохранённому запуску. Сравнение нескольких запусков допустимо только после полностью готового основного сценария, если хватает времени; без выдуманных процентов улучшения.

## 4. Язык интерфейса и продуманные состояния

Весь основной UI на русском. Термины расшифровывай в контексте: «ARPU — средняя выручка на абонента», «Пилот — небольшая проверка предложения», «Контакты — все попытки связи, включая повторные». Не заставляй читать учебник, чтобы нажать кнопку.

Формат чисел `ru-RU`: разряды разделяются пробелами, денежные значения подписаны «у.е.». `0.12` превращается в `12%` один раз. Отсутствующее значение — «Пока нет оценки»/«—», не «0». Нулевой бюджетный расход push не превращается в бесконечный ROI; сам ROI без корректного источника не показывай.

Обязательные состояния: начальная загрузка, пустые данные, нет запусков, активный расчёт, готовый положительный план, отрицательный прогноз, недостаток данных, серверная ошибка, отсутствие соединения и восстановление. Skeleton сохраняет геометрию экрана. Ошибка объясняет следующий шаг и сохраняет доступные результаты.

Никаких неработающих кнопок, случайных ссылок, фиктивных уведомлений и форм без обработки. Не добавляй sign-in, настройки аккаунта, оплату, чат с AI и переключатель темы просто для заполнения навигации.

## 5. Техническая реализация и деморежим

Используй React + TypeScript + Vite. Для маршрутов, серверного состояния, доступных primitives и графиков выбери небольшой проверенный набор библиотек; зафиксируй реально устанавливаемые версии и lockfile. Структура по смыслу: `app/`, `features/overview`, `features/audience`, `features/runs`, `components/ui`, `lib/api`, `mocks`.

Единый типизированный API-клиент реализует контракт. Экран не должен напрямую импортировать fixtures или отдельно придумывать модель ответа. Повторно используй форматирование, обработку ошибок и компоненты статусов. Не вычисляй на клиенте экономическую оптимизацию, posterior и сумму эффекта с пересечениями.

Пока backend разрабатывается, сделай **явный деморежим** через `VITE_DEMO_MODE=true` с теми же HTTP-форматами, например используя MSW. В demo допустим управляемый сценарий событий, но он подписан как демонстрация. Подготовь согласованные fixtures: пустое состояние, running, completed, отрицательный прогноз и ошибка. Бюджеты, контакты, пилоты и кампании в fixtures должны быть арифметически согласованы.

При выключенном demo и недоступном API показывай ошибку подключения. Нельзя автоматически подменять реальные данные красивыми демонстрационными. Переключение на настоящий backend не требует переписывать экраны.

Используй polling по контракту, останавливай его на completed/failed, освобождай запросы при unmount. Сохраняй в URL run_id и параметры просмотра; сервер — источник истины для результата. При сетевой ошибке не теряй уже показанный snapshot.

Управляй загрузкой CSV/JSON как файлами с обработкой ошибок, правильными именами и освобождением object URL. Не экспортируй HTML ошибки под видом CSV.

Добавь `.env.example`, README, команды `npm run dev`, `npm run build`, `npm run lint`, `npm run test` и `npm run test:e2e`, если вводишь соответствующие проверки. Не коммить секреты; frontend не требует API-ключей LLM.

## 6. Адаптивность и доступность

Проверь композицию минимум на 1440, 1280, 768 и 390 px. На узком экране sidebar превращается в доступную компактную навигацию; у таблиц сохраняются основные значения, дополнительные — в раскрытии/drawer. Горизонтальная прокрутка допустима внутри обозначенной таблицы, не у всей страницы.

Контраст обычного текста — не ниже 4.5:1. Все действия доступны с клавиатуры, focus заметен. У полей есть label, у icon-only кнопок — доступное имя. Drawer/dialog удерживает focus, закрывается Escape и возвращает focus на исходный элемент. Статус не кодируется одним цветом. Изменение этапов озвучивается через умеренный aria-live без спама на каждом polling.

Не полагайся только на hover. Кнопки и интерактивные области достаточно крупные. Длинные названия тарифов, большие суммы, минусы и пустые значения не ломают верстку.

## 7. Приёмка

Проверь сборку, типы и lint. Добавь несколько значимых UI/E2E-проверок: создание run → прогресс → результат → экспорт; восстановление после reload; повтор запроса не создаёт второй run; сетевой сбой не включает demo; отрицательный прогноз не выглядит положительным; drawer управляется клавиатурой. Не трать время на тесты каждого декоративного div.

Запусти приложение и проверь основные экраны в браузере, включая узкий viewport. Исправь переполнения, скачки layout, ошибки консоли, пустые ссылки и непонятные подписи. Если браузерная проверка недоступна, честно укажи, что не проверено; не придумывай screenshots и результаты.

Когда backend доступен, выключи demo и выполни общий сценарий из `docs/team/API_CONTRACT.md`: настоящие overview → запуск → пилоты → план → экспорт того же run. Если backend ещё не готов, закончи всю независимую часть, проверь контрактные fixtures и укажи точный оставшийся шаг интеграции.

Результат: готовый `frontend/`, премиальный согласованный UI, все состояния, явный деморежим, рабочий API-клиент, проверенная сборка и README. В финальном сообщении дай команды запуска, фактические проверки и статус реальной интеграции. Дизайн считается готовым, когда человек понимает решение и может пройти весь сценарий, а не только когда главный экран красиво выглядит.
