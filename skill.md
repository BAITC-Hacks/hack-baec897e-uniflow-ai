# ИИ-разработчик решения Beeline

## Назначение и границы задачи

Помогай разрабатывать автономного агента, который исследует аудиторию пилотами
и максимизирует `net_arpu_gain` при конкурсных ограничениях. Основной результат
полной реализации — работающий `participant_package/agent.py` и воспроизводимый
`participant_package/submission.csv`, подтверждённые запусками.

Выполняй текущий запрос пользователя в его пределах. Исправление документации
или отдельной функции не означает поручения реализовать весь проект. При запросе
полного решения доводи работу до проверенных артефактов. Общайся и веди проектную
документацию на русском; имена полей и API сохраняй как в исходном пакете.

Данные кейса синтетические. `net_arpu_gain` — моделируемый прирост выручки минус
коммуникации, а не полная прибыль или доказанный эффект для реального Beeline.

## Контракт, который нельзя потерять

- Точка входа: `Agent().act(env) -> list[dict]`; возвращать **1–10 финальных
  кампаний**. Минимум один успешный пилот; ответы должны влиять на решения.
- Доступ агента: `env.customer_profile`, `env.tariffs`, `env.channels`, публичные
  лимиты и их остатки, `env.pilots_left`, `env.pilot_history`, `env.run_pilot`.
- Лимиты: 100 000 у.е.; 15 000 контактов, включая пилоты и повторы; до 5 000
  клиентов на кампанию; до 20 пилотов с запрашиваемым размером 10–200.
  Остатки ресурсов читай из среды, не считай их неизменными константами.
- Каналы: `push`, `sms`, `digital_ads`, `call`. Стоимость и множитель брать из
  `env.channels[channel]["cost_per_contact"]` и `["conversion_multiplier"]`.
- Поля финальной кампании и порядок колонок CSV:

  ```text
  campaign_name, filter_arpu_segment, filter_data_segment, filter_call_segment,
  filter_current_tariff, target_tariff, channel
  ```

- `target_tariff` и `channel` обязательны. Тариф проверять по
  `env.tariffs["tariff_plan_code"]`. Имя кампании делай стабильным.
- Фильтры: ARPU — `LOW/MID/HIGH`; data — `NON_USER/LITE/HEAVY`;
  call — `LOW/MEDIUM/HIGH` (обрати внимание на `MID` и `MEDIUM`). Несколько текущих
  тарифов задаются одной строкой через `;`. Отсутствие фильтра — пропущенное поле
  или `None`; пустая строка не означает «все клиенты».
- В финальном контракте нет `explicit_ids`, `top_k`, `n_customers`, произвольных
  ID или фильтра по `predicted_arpu`. `n_customers` передаётся только в пилот;
  `explicit_ids` — внутренняя запись среды, не инструмент агента.
- Предел исполнения `act` — 10 минут; ориентир разработки — менее 5 минут с
  резервом на финальный план. Измеряй длительность на доступной машине.

Изучать публичный код механики разрешено. В исполняемом агенте не извлекай
скрытую модель, RNG, seed или ID пилотов через замыкания, introspection, `gc`
или внутренние файлы. Не импортируй `_mock_impact_model`, `_mock_fallback`
и не воспроизводи генератор mock-эффектов как источник ответов. Среду и известные
тестовые модели можно создавать в отдельном тестовом коде, передавая агенту
только публичный `env`. Исходные CSV и организаторские evaluator/шаблон сохраняй.
Не меняй профиль, справочники и счётчики `env` для влияния на оценку; преобразования
данных делай в собственных копиях, ресурсы расходуй через публичный вызов пилота.

## Денежная цель и исполнение

Для клиента `i`: baseline `b_i = predicted_arpu`; относительный эффект перехода
`d`; вероятность перехода `p`; множитель канала `m`; эффект `r = d * min(p*m, 1)`.
`d` и `p` скрыты: агент их оценивает, а не считывает из среды.

```text
gross = сумма по контактированным i [max по выполненным для i кампаниям (b_i * r_i)]
cost  = сумма по всем выполненным кампаниям (фактические контакты * цена канала)
net_arpu_gain = gross - cost
```

Пилоты и финальные кампании входят в одну сумму. Неконтактированный клиент даёт
нулевой прирост; у контактированного отрицательный лучший эффект НЕ обнуляется.
Не подменяй итог скоринга суммой шумных `observed_lift_total`.

1. Сначала исполняются пилоты, затем финальные кампании в возвращённом порядке.
2. Финальная аудитория: разрешённые фильтры → сортировка `ID_NUMBER` по возрастанию
   → первые 5 000 → обрезание по оставшимся контактам и деньгам. Сортировка по
   `predicted_arpu` в агенте не меняет аудиторию evaluator.
3. Повтор одинаковой кампании выбирает тех же первых клиентов. На клиента
   засчитывается лучший эффект, но оплачиваются все контакты и расходуется охват.
4. Итоговые пересечения финальных кампаний вычисляй точно. Пилот случайно
   выбирает клиентов из своего сегмента; их ID агенту не возвращаются.
   Пересечение с пилотами оценивай по фильтрам и фактическому размеру либо
   моделированием с фиксированным RNG; явно обозначай приближение.
5. `env.remaining_*` после `act` учитывает только пилоты. Полные затраты проверяй
   по `score_campaigns`. Поле отчёта `n_campaigns` включает пилоты; ограничение
   10 относится к возвращаемому финальному списку.

## Данные и обучение по пилотам

- На первом этапе проверь типы, уникальность `ID_NUMBER`, пропуски, допустимые
  сегменты/тарифы и сумму `predicted_arpu`. Размеры выборок вычисляй из CSV.
  Готовый `arpu_segment` основан на `ARPU_3m_avg`, не пересоздавай его из baseline.
- Не заполняй отсутствующий текущий тариф выдуманным тарифом. Для первой версии
  исключай такие строки из адресных кандидатов, отражая потерю охвата в аудите.
- ID истории переходов и целевой аудитории в выданном наборе не пересекаются.
  Строй групповые prior, не соединяй эти выборки по ID. История содержит только
  состоявшиеся переходы: популярность тарифа в ней не равна вероятности отклика
  на предложение и не доказывает причинный эффект.
- Исторический prior: `(AVG_ARPU_NEXT_3M - AVG_ARPU_PREV_3M) / AVG_ARPU_PREV_3M`,
  с явной обработкой малых знаменателей/выбросов, сглаживанием редких групп
  и широкой неопределённостью. `AVG_ARPU_NEXT_3M` — исход, не входной признак.
  Предусмотри работу без исторического файла с менее информативным prior.
- Единица оценки: `current_tariff × arpu_segment × target_tariff` и канал.
  `data_segment`/`call_segment` помогают управлять составом и размером аудитории;
  отдельный эффект от них не задан публичной механикой.
- Для однородного пилота используй `observed_lift_ratio` и возвращённый
  `n_customers`: дисперсия шума `0.804**2 / n_actual`. Фактический размер может
  оказаться меньше 10. Не используй запрошенный размер вместо фактического.
  Смесь исходных групп нельзя обновлять как однородное наблюдение каждой группы.
- Храни собственный журнал параметров запроса и ответа: `env.pilot_history`
  не сохраняет все фильтры. После пилота обновляй оценки и исполнимый план.
- При переносе между `push/sms/digital_ads`: `q = ratio / m`, дисперсия также
  делится на `m**2`. У `call` возможно насыщение `min(p*1.2, 1)`; нельзя всегда
  умножать push-эффект на 2.4. Для существенных расходов на звонки нужен свой
  пилот или консервативная модель насыщения.

## Порядок разработки и улучшений

Для полной реализации двигайся от проверяемого минимального решения:

1. Аудит данных и контракта; измеренный baseline из `agent_template.py` через
   отдельный запуск, без подмены рабочего `agent.py` или evaluator.
2. Генератор допустимых кандидатов, кэш масок и точный учёт ресурсов/пересечений.
3. Слабый prior, обновления после пилотов, рабочий непустой финальный план.
4. Адаптивный выбор гипотез и размеров пилота с резервом денег, контактов
   и времени. Проверяй, что разные ответы меняют дальнейшие действия.
5. Выбор портфеля по добавочному **денежному** эффекту с учётом порядка и
   неопределённости; затем ограниченный поиск замен/перестановок, если полезен.
6. Измеренные сравнения, проверки воспроизводимости, подготовка сдачи.

Не зашивай выигрышные тарифы, фиксированное исчерпание всех 20 пилотов или
оптимальность одного канала. Бесплатный push расходует контакты и может давать
отрицательный эффект. `gain/cost` некорректен для нулевой стоимости и сам по себе
не решает задачу портфеля. Размер shortlist, сила prior, риск-штрафы и стратегия
поиска — гиперпараметры для экспериментов, а не требования организаторов.

Держи в памяти лучший корректный план текущего запуска. При всех отрицательных
оценках выбери допустимую непустую кампанию с минимальным ожидаемым ущербом,
сохрани резерв для её исполнения и запиши риск. Пустой фильтр или переход на тот
же тариф не являются гарантированно безопасным решением. Ошибки не скрывай:
логируй контекст и перечитывай публичные остатки среды перед следующим действием.

## Реализация и воспроизводимость

- Основной стек: Python, pandas, numpy; pytest для содержательных проверок.
  Сначала проверяй установленную среду и `participant_package/requirements.txt`;
  не объявляй версии рабочими без успешного запуска.
- Для сдачи предпочитай самодостаточный `agent.py`. Собственные модули и файлы
  включай в поставку; пути к данным вычисляй относительно модуля, без абсолютных
  путей разработчика и состояния notebook. Не создавай лишнюю инфраструктуру.
- Все изменяемые оценки, журнал и RNG инициализируй для каждого `act` заново.
  Используй локальный RNG с фиксированным seed для воспроизведения при
  `SUBMISSION_SEED=42`; не считывай скрытый seed среды. Задавай стабильный порядок
  кандидатов и разрешение равенств. Ограничивай поиск числом итераций;
  монотонный таймер используй как аварийный предел, не источник случайности.
- Ядро работает без сети, LLM и ключей. LLM и интерфейс добавляй по задаче после
  проверенного ядра. Необязательная LLM получает timeout, ограничение запросов,
  валидацию ответа и fallback; арифметика и ограничения остаются в коде.
  Ключ — только из окружения. По умолчанию LLM не меняет воспроизводимую сдачу.
- Локальные пилоты относятся к симуляции. Разработка не означает разрешения
  отправлять реальные маркетинговые кампании или публиковать результаты вовне.

## Проверка готовности

Организаторские скрипты читают CSV относительно рабочего каталога. Запускай
команды из `participant_package/`, в PowerShell переходи туда один раз:

```powershell
Set-Location participant_package
python -m pip install -r requirements.txt
python local_eval.py
python local_eval.py --runs 10
python make_submission.py
$firstSubmissionHash = (Get-FileHash -LiteralPath submission.csv -Algorithm SHA256).Hash
python make_submission.py
if ((Get-FileHash -LiteralPath submission.csv -Algorithm SHA256).Hash -ne $firstSubmissionHash) {
    throw 'submission.csv не воспроизводится'
}
```

Установку выполняй при подготовке окружения, а не при каждом прогоне. После
создания тестов запускай `python -m pytest -q`; экспериментальные команды
документируй по фактически созданным скриптам. Одного exit code недостаточно:
`local_eval.py` может перехватить падение агента, а sanitizer — отбросить кампании.
Проверяй число финальных кампаний, успешные пилоты, сообщения и итоговые ресурсы.

Проверки выбирай по изменению. Для полной реализации нужны:

- Небольшие примеры на сортировку/обрезание, порядок кампаний, повторы, бюджет,
  контакты, отрицательный максимум и фактический размер пилота.
- Проверка обновления posterior, насыщения `call`, реакции на разные ответы,
  пустых сегментов, отказов необязательных компонентов и сброса состояния `act`.
- Сравнение с шаблоном на одинаковых seed, затем на отдельных тестовых сценариях
  со сменой лидеров/знаков, слабым prior, малой конверсией и насыщением.
  Несколько seed одной mock-модели проверяют шум, но не сдвиг скрытых эффектов.
- Сравнение ключевых компонентов через ablation. Фиксируй реальные mean,
  median, min, p10 `net_arpu_gain`, долю отрицательных прогонов, стоимость,
  контакты и runtime. Не обещай превосходство, если измерения его не подтвердили.
- Два совпадающих CSV при seed 42, корректная схема/значения и запуск сдаваемого
  набора файлов в чистой копии. `submission.csv` генерируй, не редактируй вручную.

Для полного решения сохраняй в `participant_package/`: `agent.py`,
`submission.csv`, зависимости, `tests/`, `experiments/`,
`reports/data_audit.json`, `reports/benchmark.csv`, `reports/ablation.csv`,
`reports/decision_trace.json`; обновляй существующие `docs/contract.md`,
`docs/approach.md` и корневой README с командами запуска. Создавай артефакты
по мере реализации; не заполняй отчёты выдуманными результатами.

В ответе о проделанной работе указывай изменённые файлы, выполненные проверки,
измеренный результат и оставшиеся ограничения. Различай наблюдение на mock,
оценку алгоритма и неизвестный результат на судействе. Если проверка недоступна,
назови причину и не объявляй её пройденной.
